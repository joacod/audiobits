# Product finish roadmap

The recipe/runtime foundation, eight-sound gallery and private candidate are
implemented. Publication and deployment remain disabled. Architecture stays
fixed unless a real sound or experience is blocked by the existing vocabulary.

1. **API/scaffolding cleanup:** remove development markers and effect-specific
   bus setters; keep typed parameter inference and authoritative runtime validation.
2. **Listening and tuning:** deliberately hear all eight sounds at defaults,
   control extrema, varied seeds, repetition and overlap on headphones and speakers.
   Tune from observations; automated signal checks remain separate evidence.
3. **Public showcase:** an intentional first sound, semantic morphing, real output
   visualization and concise code, separate from the calm Fumadocs reference.
4. **Physical browser/device verification:** desktop Chrome, Firefox and Safari;
   iOS Safari and Android Chrome when accessible. Record actual devices and gaps.
5. **Final 0.1 readiness:** API/doc consistency, automated browser matrix, package
   rehearsal and human acceptance for the exact candidate.
6. **Initial npm and site release:** independently approve the exact npm artifact
   and site deployment. Keep both actions disabled until that approval.

Completed cleanup and showcase implementation are no longer release blockers;
listening/tuning, physical checks and final candidate acceptance remain open.

Post-0.1 candidates include MCP, devtools, new sounds, shared-effect requirements,
spatial systems and registry/packs. They are not initial release blockers. Adapters,
worklets, WASM, offline caching, sequencing and MIDI need a demonstrated reusable
requirement. Do not expand release machinery without a real failure.
